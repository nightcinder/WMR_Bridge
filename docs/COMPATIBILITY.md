# Firmware and Library Compatibility Matrix

This document defines the compatibility contract between the WMR_Bridge bridge targets
(the default ESP32-over-BLE firmware in `src/` and the second supported
Linux / Raspberry Pi-over-Wi-Fi host bridge in `pi/`, see
[`docs/PI_BRIDGE.md`](PI_BRIDGE.md)) and the `wmr-companion` Flutter/Dart client
library packages. The key is the FF16 firmware version characteristic (for BLE
firmware) or the WebSocket `hello.version` field (for the Pi Wi-Fi bridge, which
does not expose a GATT FF16 characteristic).

This document is the canonical copy of the compatibility matrix. The client library
repository references this document from `docs/LIBRARY.md` section 9 and
`packages/wmr_companion/README.md` rather than maintaining a duplicate copy that
could drift.

---

## Important Status Notices (Stated Explicitly)

1. The client library is not published.
   The Companion app on `main` builds against the Dart packages at `0.3.0`.
   The released `v0.3.17` tag pins the `0.2.2` packages. The Dart package
   breakdown below lists twelve packages:
   `wmr_core`, `wmr_companion`, `wmr_ble`, `wmr_ws`, `wmr_fusion`,
   `wmr_tracking`, `wmr_tracking_dispatch`, `wmr_tracking_android_xr`,
   `wmr_tracking_viture`, `wmr_tracking_xreal`, `wmr_companion_ui` and
   `wmr_companion_hid_android`. All twelve are at version `0.3.0` in git source
   within a Dart pub workspace. The reference app uses `ControllerService`
   directly, and `example/` uses the `WmrCompanion` facade. Publication to pub.dev
   is on hold by the owner's decision (2026-10-23, ONY-41). See the `wmr-companion`
   repository docs `docs/PUBLISHING.md` section 5 and `docs/LIBRARY.md`. The
   package versions in this matrix refer to source and git checkout versions,
   not to pub.dev releases. None of these packages are available on pub.dev.

2. The firmware releases `v0.1.0-rc1`, `v0.1.0` and `v0.2.0` through `v0.3.13` are
   CI-built and hardware-unverified, and the Pi bridge is host-tests-only.
   Firmware releases `v0.1.0-rc1` (commit `547ab09`, prerelease), `v0.1.0`, and
   `v0.2.0` through `v0.3.13` (`0.3.13` is the latest release) are
   hardware-unverified: CI compiled and packaged the release artifacts (all three
   bridge variants plus the browser flasher), but no physical board flashed with
   these packaged releases has been tested or confirmed to function. Likewise, the
   Linux/Raspberry Pi Wi-Fi host bridge (`pi/`, merged in #47), the PSVR2
   Sense controller path (merged in #46, searched by default from 0.2, with
   FF12/FF14 decode added in #142) and the Switch Joy-Con/Pro path (#144) are
   host-tests-only and have never run on a Raspberry Pi, PSVR2 or Switch
   controller; the Switch hardware check is tracked in GitHub #145. The Pi
   package caches and forwards FF13 calibration blobs but does not read them
   from a controller. No
   row in this matrix implies hardware validation beyond what is explicitly noted
   in [`docs/STATUS.md`](STATUS.md).

## Compatibility Matrix (Keyed on FF16 Version / WebSocket `hello.version`)

The ESP32 BLE bridge exposes its firmware version over GATT characteristic FF16
(`0000FF16-0000-1000-8000-00805F9B34FB`) as a read-only UTF-8 string with no
terminator (up to 31 bytes). The Linux / Raspberry Pi Wi-Fi host bridge does not
run a GATT server. It reports its software version in the initial WebSocket
`hello` control message (`"version": "0.3.13"` for the `pi/` package in this
tree, protocol 1 on `wmr-wifi-v1`). The `v0.3.12` release shipped the `0.2.4`
package; `v0.3.13` ships the `0.3.13` package. `wmr_ws`
surfaces that through the `read(FF16)` seam without a network round trip.

The table below describes every bridge era/target and how the client library
interacts with it:

treats `1` as a valid FF16 string without error.

## GATT Characteristic Capability Table

The capability matrix is discovered from the bridge's GATT table upon connection
rather than inferred solely from the version string:

| Feature Flag (`WmrBridgeFeatures`) | Characteristic | UUID | When the bridge offers it | Client Notes |
| --- | --- | --- | --- | --- |
| `rawStream` | FF11 | `0000FF11-0000-1000-8000-00805F9B34FB` | Every known firmware | Raw controller HID reports fragmented into BLE notifications. Read returns a 16-byte status block. |
| `decodedStream` | FF12 | `0000FF12-0000-1000-8000-00805F9B34FB` | Every firmware with the decoded stream | Decoded 56-byte records. Mutually exclusive with FF11 and FF14. |
| `batchedStream` | FF14 | `0000FF14-0000-1000-8000-00805F9B34FB` | Firmware with batching | Batched decoded records. Requires ATT MTU at least 61: firmware accepts subscription but drops records as `mtu_skip` when MTU is below 61. The client facade's stream selection requires ATT MTU at least 61 and surfaces ATT error `0x80` if refused by exclusion rules. |
| `configBlock` | FF13 | `0000FF13-0000-1000-8000-00805F9B34FB` | Firmware with the config block (WMR_Bridge #17) | Read-only access to the controller calibration/config block in 496-byte windows with CRC-32 verification. |
| `echo` | FF15 | `0000FF15-0000-1000-8000-00805F9B34FB` | Firmware with echo (WMR_Bridge #13) | Diagnostic ping/pong for round-trip latency measurement. Independent of stream mode. |
| `firmwareVersion` | FF16 | `0000FF16-0000-1000-8000-00805F9B34FB` | Firmware with #38 (`41771f8`) and later | Read-only UTF-8 version string (`PROJECT_VER`, max 31 bytes). Independent of stream mode. |
| `controllerControl` | FF17 | `0000FF17-0000-1000-8000-00805F9B34FB` | Firmware with WMR_Bridge #70 (`v0.1.1`) and later | Controller scan, connect, disconnect and forget commands, plus a 20-byte status v2. FF17 is unencrypted on firmware `v0.1.1` to `v0.2.4`. Firmware `v0.3.0` to `v0.3.4` (#88) declares `READ_ENCRYPTED` and `WRITE_ENCRYPTED` but does not enforce them. From `v0.3.5` (#132), read, write and notify require a bonded encrypted link with a 16-byte key. Independent of stream mode. |

### Client Compatibility Rules

- A bridge with no FF16 is an older firmware and a normal status: `protocol.firmwareVersion` is `null` and `features.firmwareVersion` is `false`. The rest of the matrix still describes what that bridge can do.
- Fail-soft protocol: unknown characteristics are ignored. Callers and client libraries must ignore records or fields their code does not recognize instead of treating them as fatal.
- PHY is not a gap or to-do: the bridge hardware is an original ESP32 (Bluetooth 4.2). 2M PHY is a Bluetooth 5.0 feature and cannot be supported by this chip. In client connection information, `BleConnectionInfo.phy` remains `null` on every platform because PHY is not observable by the host stack, not because 1M was confirmed by reading.

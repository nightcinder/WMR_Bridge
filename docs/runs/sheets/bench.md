# Minimum bench run sheet

Hardware: Raspberry Pi 3B+, ESP32 (v0.3.28-rc.3 candidate), LEFT and RIGHT WMR controllers, Pixel 11 Pro running wmr_companion_app v0.3.26. Target time is about 26 minutes.

## Prerequisites

1. Set `WMR_BRIDGE_ARGS="--idle-sleep-timeout 30 --idle-poweroff-timeout 90"` in `/etc/wmr-bridge/wmr-bridge.env` on the Pi (`pi/systemd/wmr-bridge.service:13,25`).
2. Restart the daemon with `sudo systemctl restart wmr-bridge`.
3. Pair the phone to the Pi over Bluetooth in Android Settings (`docs/HID_GAMEPAD.md:481-523`). If pairability is off, open a pairing window with `wmr-bridge pair` (`docs/HID_GAMEPAD.md:542-560`, `pi/wmr_bridge/ble_gatt.py:2121-2144`). Run `wmr-bridge status` to confirm that the stored LE bond note appears with `pairable=no` (`pi/wmr_bridge/__main__.py:605-612`), or verify `Paired: yes` with `bluetoothctl info <MAC>`.
4. Isolate or unplug `eth0` before the Wi-Fi failover and recovery steps so that network routing stays unambiguous.
5. When the 60 s cooldown expires, the pairer reconnects the bonded controller automatically (`pi/wmr_bridge/inputs.py:184-201,418-432`, `pi/wmr_bridge/bluez.py:1046-1052,1288-1308`). If the controller stays offline, press a physical button to wake it. Motion wakes the controller only from stage 1 idle sleep.

## Part A: Raspberry Pi 3B+ (~12 min)

1. Boot and uplink (PR #187, #188). Start `wmr-bridge` on Pi 3B+ with the prerequisites configured. Pair LEFT and RIGHT controllers. Run `wmr-bridge status`.
   - [ ] PASS / FAIL: Both controllers connected. Uplink matches the active interface (`eth0` metric 100 or `wlan0` 5 GHz metric 200). The adapter's BlueZ name follows the Pi host name (`wmr-bridge`; `wmr-bridge status` prints it, `pi/wmr_bridge/__main__.py:586-590`), mDNS advertises `_wmr-bridge._tcp` as `wmr-bridge.local` (`pi/wmr_bridge/mdns.py:29,54,101`), and BLE advertises `WMR Bridge` (`pi/wmr_bridge/__main__.py:295-296`). Stored LE bond note appears with `pairable=no` (`pi/wmr_bridge/__main__.py:605-612`) or `bluetoothctl info <MAC>` confirms `Paired: yes`.
2. UDP discovery and Sitting P gates (PR #193). Run `sudo python3 /opt/wmr-bridge/pi/tools/wifi_probe.py --discover --assert-gates --duration 30 --token-file /etc/wmr-bridge/token --json-out /tmp/pi_probe.json` while moving both controllers (`pi/build_deb.sh:106`, `pi/install.sh:438`).
   - [ ] PASS / FAIL: Run seated with both controllers at <=2 m and a clear line of sight, the nominal range in `ONY-1509`; the 2026-11-18 run was about 20 ft behind furniture (`docs/runs/2026-11-18-pi-bench.md:53-59`). Command exits 0. UDP port 8765 discovered (`pi/wmr_bridge/discovery.py:28`, `pi/tools/wifi_probe.py:48`). RTT p50 under 15 ms. Missing share at most 3.0% per hand. Zero sequence gaps. Server drops (`dropped`) are 0 (observed, not a gate).
3. LAN auto-connect and daemon CPU (M2). Open `wmr_companion_app` on Pixel 11 Pro on the same LAN. Sample mean daemon CPU for 10 minutes with `top -b -n 60 -d 10 -p MainPID`. Here `MainPID` is the daemon PID from `systemctl show -p MainPID --value wmr-bridge.service` (`pi/wmr_bridge/mdns.py:81-90`, `wmr-companion docs/TEST_PLAN_PI_WMR.md:97`).
   - [ ] PASS / FAIL: App auto-discovers Pi via UDP port 8765 and streams both hands over TCP at 150-180 reports/s per hand (`pi/wmr_bridge/discovery.py:28`). The sample covers the whole daemon process, not the decode step alone. The gate depends on the board (decision, ONY-1583). The companion plan still sets one 25%/50% gate for every board. The split lands there in ONY-1584. On a Pi 4 or Pi 5, mean daemon CPU stays below 25% of one core, and no 10 s sample goes above 50%. On a Pi 3B+, the interim gate is mean at or below 38.5% and no 10 s sample above 40.5%. That baseline is 61 samples from the 2026-11-18 run (ONY-1159 comment `0efef418`, document `bench-run-2026-11-18`, archived at `docs/runs/2026-11-18-pi-bench.md:32`). The interim 3B+ gate stays in force after the per-report CPU cut (ONY-1507 child 4). Record the board and the sample count with the result.
4. TCP-to-BLE failover. Make sure that `eth0` is unplugged. Start streaming to Pixel 11 Pro. If you use SSH, run `sudo /opt/wmr-bridge/pi/tools/bench_failover.sh --detach` on the Pi (`pi/tools/bench_failover.sh:14-15,94-99`). The script takes `wlan0` down for 10 s (`pi/tools/bench_failover.sh:19,124-128`). An SSH session over `wlan0` drops when the interface goes down (`pi/tools/bench_failover.sh:120`). The detached child process survives under `nohup` and restores `wlan0` after 10 s (`pi/tools/bench_failover.sh:94-99,101-116`). If you use a local console, you can run `sudo ip link set wlan0 down`.
   - [ ] PASS / FAIL: CompositeBleTransport fails over to BLE GATT within 2500 ms with continuous pose updates.
5. BLE-to-TCP recovery. If you used `bench_failover.sh`, read T0 and T1 from `/tmp/failover.log` (`pi/tools/bench_failover.sh:21,132,145-148`). Record T2 when the app reports TCP streaming. If you test manually, run `sudo ip link set wlan0 up` on the Pi. Record T0 when you run the command and T1 when `ip -o -4 addr show wlan0` reports an IPv4 address.
   - [ ] PASS / FAIL: T2 - T1 <= 5 s and T2 - T0 <= 15 s, with no app restart (`ONY-1456`).
6. Pi idle sleep and wake (PR #190). Leave both controllers untouched for 35 s, then tilt LEFT.
   - [ ] PASS / FAIL: Journal logs keep-alive paused at about 30 s. Tilting wakes the stream within 1 s.
7. Pi idle power-off and reconnect guard (PR #190). Leave both controllers untouched for 95 s under the 30/90 s override from prerequisite 1.
   - [ ] PASS / FAIL: Journal logs the BlueZ block at about 90 s and both LED rings turn off. The expected log trace is `idle for <N> s: disconnecting...to power it off` followed by `bluetoothctl block <addr>` (`pi/wmr_bridge/inputs.py:444-478`, `pi/wmr_bridge/bluez.py:616-645`). The BlueZ block drops the ACL link, followed by `bluetoothctl disconnected <addr>` or `bluetoothctl <addr> already disconnected` (`pi/wmr_bridge/inputs.py:487-495`, `pi/wmr_bridge/bluez.py:585-613`). No `connected` line appears during the 60 s cooldown (`pi/wmr_bridge/inputs.py:260-266,470-477`). Wait until the log reports `power-off cooldown elapsed: reconnects allowed` and `bluetoothctl unblock <addr>` (`pi/wmr_bridge/inputs.py:418-432`). The pairer reconnects the bonded hand automatically (`pi/wmr_bridge/inputs.py:184-201`, `pi/wmr_bridge/bluez.py:1046-1052,1288-1308`). If LEFT stays offline, press a physical button on LEFT to reconnect and stream. Stop Pi `wmr-bridge` before you start Part B.

   Step 6 tests stage 1 idle sleep at 30 s (default 300 s in `pi/wmr_bridge/inputs.py:26`). That stage pauses keep-alive packets while keeping the Bluetooth ACL connected (`pi/wmr_bridge/inputs.py:520-538`). Controller reports can still arrive after that pause, and motion wakes the controller (`pi/wmr_bridge/inputs.py:380-392,533-538`).

   Step 7 tests stage 2 idle power-off at 90 s (default 900 s in `pi/wmr_bridge/inputs.py:27`). This stage forces an ACL disconnect and blocks incoming connections in BlueZ for a 60 s cooldown (`pi/wmr_bridge/inputs.py:444-495`). Motion cannot wake a powered-off controller. After the 60 s cooldown expires, the pairer reconnects the bonded hand automatically (`pi/wmr_bridge/inputs.py:184-201,418-432`, `pi/wmr_bridge/bluez.py:1046-1052,1288-1308`). If the hand stays offline, a physical button press also reconnects it (`pi/wmr_bridge/inputs.py:418-432`).

8. Restart-safe adapter recovery (ONY-1499). Record `systemctl show -p ExecMainStartTimestamp wmr-bridge` and `systemctl show -p ExecMainStartTimestamp wmr-bridge-bt-recover` before the cycle. Run `sudo systemctl restart wmr-bridge` twice, then copy the built `dist/wmr-bridge_<version>_all.deb` (`pi/build_deb.sh:4-5`) to the Pi and run `sudo apt-get install --reinstall ./wmr-bridge_<version>_all.deb`, which re-runs `pi/debian/postinst:114` (the daemon's `--upgrade` is a no-op when the installed version is current, `pi/install.sh:287-297`).
   - [ ] PASS / FAIL: After each of the three commands, `timeout 10 sh -c 'until bluetoothctl show | grep -q "Powered: yes"; do sleep 1; done'` exits 0. The 10 s gate is a healthy-path regression guard, sourced to ONY-1499 items 1 and 3 and the two clean rc.2 restarts in ONY-1498 `rc2-restart-test`, not the 30 s idle sleep cap. After each command, `systemctl is-failed wmr-bridge-bt-recover` does not print `failed`, and `systemctl show -p ExecMainStartTimestamp wmr-bridge-bt-recover` still prints the value recorded before the cycle, so a recovery run inside the gate fails the step. After each command, `journalctl -k -b 0` contains no `Opcode 0x0c03`. After the reinstall, `systemctl show -p ExecMainStartTimestamp wmr-bridge` prints a later timestamp than the one recorded before it.

## Part B: ESP32 (~14 min)

9. ESP32 BLE GATT stream. Boot ESP32 (v0.3.28-rc.3). Power on both controllers. Connect Pixel 11 Pro over BLE in `wmr_companion_app`.
   - [ ] PASS / FAIL: Both hands stream over BLE characteristic 0xFF14 at 150-180 reports/s per hand. Zero disconnects over 60 s.
10. FF16 version and FF17 control (Block B). In `wmr_companion_app` (`v0.3.26`), tap "Open 3D debug view" on the connect screen (`connect_screen.dart:436-445`). Find the FF16 firmware line under the "Stream" heading (`debug_screen.dart:205-213,523-556`, `wmr_ws_transport.dart:285,338-340`). Check the firmware version. In `ControllerPanel`, tap disconnect on LEFT (0xFF17) and reconnect LEFT (`debug_screen.dart:229-235`). Note that `ControllerPanel` (FF17) is hidden on Wi-Fi bridges and is tested on ESP32 BLE only.
   - [ ] PASS / FAIL: FF16 version matches serial `v` output. FF17 drops LEFT cleanly and reconnects within 5 s.
11. Five-minute active keep-alive and Android HID check. Keep controllers moving or tapped for 5 min 30 s while connected to ESP32. While HID and BLE stream together, inspect Android input registration with `adb shell dumpsys input | grep -E -A 25 -i "wmr[- ]bridge"` (`docs/HID_GAMEPAD.md:481-523`).
    - [ ] PASS / FAIL: No controller powers off during more than 5 min of active use. Zero unexpected ACL drops. Android registers `WMR Bridge` with no HID slot starvation.
12. ESP32 idle sleep and motion wake (PR #191). Leave both controllers untouched for 5 min 15 s. Check serial log. Tilt both controllers.
    - [ ] PASS / FAIL: Serial logs `FF13 LEFT: idle for <N> ms; keep-alive paused, controller may sleep` (and RIGHT), with N between 300000 and 310000. Tilting logs `FF13 LEFT: activity after idle sleep; resuming the keep-alive` (and RIGHT) and resumes streaming within 1 s.
13. Bundle export. Tap Export Test Bundle in `wmr_companion_app` on Pixel 11 Pro.
    - [ ] PASS / FAIL: ZIP bundle exports with `manifest.md`, `diagnostics.json` and non-empty controller samples.

## Optional expansions

Run only when investigating a regression: (a) ESP32 full 15-min untouched power-off plus 60 s cooldown rejection (900 s wait), (b) FF13 stick deadzone and calibration persistence across reboot (3 min), (c) 3DoF 90-degree turn and 60 s yaw-drift check (5 min).
